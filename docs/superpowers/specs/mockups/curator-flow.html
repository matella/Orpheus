LLM Curator Flow — The Core Loop

What happens from "queue is running low" to "3 tracks queued with patter"

Step-by-step flow
1
Trigger — Proactive Scheduling
Engine polls Spotify every 5s. When remaining_ms < 30000 on the last planned track, fire the curator.
Also triggers on: session start, user music request, steering change (debounced 5s).
2
Assemble ListenerContext
Gather from multiple sources into one object:
top_artists / top_genres
← top-artists.repo.ts
recent_tracks / just_played
← session.repo.ts + engine state
mood + steering values
← settings.repo.ts (steering controls)
local_time + time_phrase
← system clock + context-learning.ts
DJ persona + chattiness
← dj_preferences (new table)
discovery_appetite
← dj_preferences (new table)
3
Build Candidate Pool
Three sources, ratios from user's discovery appetite:
Library 65%
Similar 25%
Discovery 10%
↑ Comfort-first default. Adjustable per user. Genre openness steering shifts ratios dynamically.
Pre-filtering: Steering axes remove mismatches before the LLM sees them.
Energy at 0.9 → drop tracks with energy < 0.5 from the pool.
Recency exclusion: Last 10 tracks + last 3 artists excluded.
Target pool size: 40–60 tracks (tuned to 7B model context).
4
Call LLM (Schema-Constrained)
Build the prompt from:
System: DJ persona prompt (selected preset or custom)
        + chattiness hint ("minimal commentary")
        + steering description ("energy cranked to 0.9")

User: ListenerContext (artists, genres, time, mood)
      + just_played + recent session
      + candidate pool (40-60 tracks formatted)

Format: JSON schema → { picks: [{track_id, reason}×3], patter: string }
Options: temperature 0.7, timeout 15s
5
Validate + Safety Net
Three validation layers:
① Pool validation
Every track_id must exist in the pool. Hallucinated IDs → dropped, backfilled from pool.
② Transition check
Algorithmic scorer checks adjacent energy deltas. Reorder if delta > 0.8 between neighbors.
③ Dedup guard
No duplicate artists in the 3 picks unless the LLM flagged it in the reason as intentional.
6
Queue + Broadcast
Load 3 picks into the queue. Sync first 2 to Spotify queue via API.
Broadcast via WebSocket:
→ ws: { type: "curator_update", picks: [...], patter: "...", source: "llm" }
→ ws: { type: "state_updated", queue: [...] }
!
Fallback Path — LLM Unavailable
If Ollama is unreachable or times out (15s):
Immediate
Fall back to existing selector (single track, algorithmic scoring). Music never stops.
Notify
WS broadcast: { type: "curator_fallback", reason: "..." }. Client shows "Auto-pilot" indicator.
Retry
Health check every 2 min. When LLM recovers, switch back to curator. WS: curator_restored.

Timing budget

Context assembly
~50ms (all local DB reads)
Pool building
~100ms (query + filter)
LLM call
2–10s (7B model, local)
Validation
~5ms (in-memory checks)
Total
~3–11s (well within 30s buffer)
